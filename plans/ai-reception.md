# 受付 — このサイトでAIが「実行」できる操作を提供する

Status: 実装中（第1弾: 誤り・更新の指摘の受付）
Issue: [#199](https://github.com/shoujiki-panman/aidoku/issues/199)

製品」を、2026-09-09 に本人が「先にやる」と決定（従来は将来機能の位置付け）。

## Why — なぜ要るか

門番はこれまで「読む」だけだった（ask で聞かれて答える）。後半の構想の中心は
**「このサイトでAIが何をできるか」という定義**を持ち、AIが操作を**実行**でき、
**成立したか・どこで止まったかが分かる**こと。これを想像で設計せず、
自分のサイトが実際に持っている受付機能で確かめる。

## 第1弾の受付: 誤り・更新の指摘

aidoku が本当に運用している受付＝「誤りの指摘を歓迎します → GitHub」（画面フッター）を
AIに公開する。**偽の予約フォームは作らない**（NEVER: 見本を本物として見せる）。

| 定義の要素 | 中身 |
|---|---|
| 何ができるか | 採点対象ページの実測値への誤り・更新の指摘を出す（= GitHub Issue が立つ） |
| 必要な入力 | `site`（対象ページURL）と `detail`（指摘の内容）。任意で `field`（4項目名）・`evidence`（根拠URL） |
| 受け付ける条件 | **署名（Web Bot Auth）の検証に成功したエージェントのみ**。人間はこれまでどおりGitHubから |
| 完了の判定 | Issue が作られ、番号とURLが返る |
| 止まったらどこかが分かる | signature / validation / not-configured / github-4xx,5xx を明示して返し、記録する |

## 完了条件（第1弾）

1. MCP（`POST /mcp`）の tools/list に受付ツールが載り、定義（必要入力・条件・完了判定）が
   description / inputSchema で読める
2. 署名検証済みエージェントが tools/call で実行すると、GitHub Issue が作られ、
   番号とURLが返る（成立の判定）
3. 署名なし・検証失敗は実行できず、理由が返る（拒否も「どこで止まったか」の1つ）
4. 入力不足は何が足りないかを列挙して返す
5. 受付の試行（成立・不成立とも）が記録に残る（KV。人間の記録は取らない方針のまま）
6. GitHub 側の失敗（4xx/5xx）は隠さず `github-<status>` として返る
7. 以上が node の unit test で機械確認できる（`gatekeeper/test_reception.mjs`）

## 制約 — 既存の決定と衝突させない

- `decisions/api-layer-from-michiyomi.md`（誰でも叩ける書き込み口を作らない）:
  受付は**署名検証済みエージェント限定**なので、匿名の書き込み口にはならない。
  LLM も呼ばない（Issue を1本立てるだけ）
- MCP の窓口は従来 NLWeb の `ask` 1本だった。受付ツールの追加は「操作の提供」という
  後半の決定によるもので、`ask` 側の NLWeb 準拠は変えない
- Issue の採否・対応は人が判断する（AIの指摘を自動で値に反映しない）

## 次の弾（この計画の残り）

- 受付の集計（成立/不成立・止まった場所）を `/_aidoku/demand` 系の出口に足す
- 更新と再検証（受付の定義が変わったときの版管理）
- 外部サイトの受付（フォーム実行=Playwright接続）は、公開された実験台ができてから
