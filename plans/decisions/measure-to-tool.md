# 測るだけで終わらせず、道具として配る

Status: 採用（2026-08-22）
Tracks: web/skill/SKILL.md, web/test_skill.mjs, index.html「自分のAIに持たせる」

## 問題

AI読はここまで「23区のサイトはAIから読みにくい」を実測して見せる**報告物**だった。
だが読めない理由が具体的に分かっているなら、その分だけ**住民側のAIを賢くできる**はずで、
報告のままにしておく理由がない。

一番の実害はスコアの低さではなく**ハルシネーション**にある。
自治体ページをそのままAIに読ませると、手数料の記載が無いページで「無料です」と答え、
期限が無いページで「通常14日以内です」と一般論で埋める。住民はそれを信じて窓口で差し戻される。
AI読は「そのページに手数料は書かれていない」を実測で持っている唯一の側なので、
その一手前で止められる。

## 選択肢

| | 中身 | 明日（提出）までに動くか |
|---|---|---|
| A | 門番（gatekeeper）を公開デプロイし、MCP `ask` で答えさせる | ✗ KVのidが未設定・Cloudflareアカウント作業が要る。区の導入も前提 |
| B | **SKILL.md 1枚を GitHub Pages から配る** | ✓ サーバー不要。既に Pages が data/ を配っている |
| C | ブラウザ拡張 | ✗ 審査・配布の手間が本題からずれる |

## 決定: B

理由は「今日から誰でも使える」こと1点に尽きる。
Pages は既に `data/*.json` を公開しており、スキルは**その上に乗るだけ**で新しい基盤を要らない。
区の許可も、デプロイも、アカウントも要らない。**住民側だけで完結する**のが本質的に強い。

A（門番）は捨てない。あれは**自治体が置く側**の解で、B は**住民が持つ側**の解。
同じ実測データを、供給側と需要側の両方から使う形になっている。

## この決定で分かったこと

スキルの記述をテストで実データに突き合わせたところ（`web/test_skill.mjs`）、
`オンライン明示` だけが 0/10/20 の**3値**（記載なし／曖昧／明記）だと判明した。
「曖昧＝10」は、オンライン申請の入口はあるが**完結するのか来庁予約だけなのか
ページから判別できない**状態で、ここを「オンラインでできます」と言い切るのが
一番害が大きい。スキルに名指しで書いた。

指示書は文字なので、参照先がズレても壊れず、AIが黙って推測に戻るだけになる。
だから**スキルにテストを付ける**（参照ファイル・フィールド名・配点・区名の実在確認）。

## 正直に言う限界

**「みんながここをベースに行政関連を調べる」には、データの範囲が全く足りない。**
いま持っているのは 23区 × 3手続きだけ。詰まるのはスキルの作りではなく**測定のスループット**で、
判定が1台のMacの `claude -p` に張り付いている限り、ここは広がらない。
道具として配る形にしたことで、**測定を増やせば増やしただけ効く**構造にはなった。
