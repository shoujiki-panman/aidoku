# 外部の変換器（anydoc）を、作品本体には入れない。検算には使う

## 問題

`crawler/officedoc.py` は400行超の手書きPDFパーサで、字形の対応表（`/ToUnicode` CMap）を
自分で解いている。**今週そこで3件バグを出した**（読めないゲートがゴミを通す /
フォント別対応表だけだと悪化する / 本文ストリームの判定ミス）。

**照らすものが自分の実装しか無い。** 手で数えていた頃の変化セル集計と同じ形で、
間違っていても気づけない。

2026-08-30、`firecrawl/anydoc`（Word/PPT/Excel/PDF/EPUB → Markdown、MIT、
`pip install firecrawl-anydoc` でビルド済みwheel）を教わった。

## 測ったこと

キャッシュ済みの添付88本を、両方に読ませて突き合わせた（`analysis/compare_readers.py`）。

| 結果 | 本数 |
|---|---|
| 両方読めたが中身が違う | 36 |
| どちらも読めない | 20 |
| 同じ | 16 |
| **anydocだけ読めた** | **9** |
| **うちだけ読めた** | **7** |

**どちらか一方が優れているのではなく、得意が分かれている。**

- **anydocだけ読めた9本**: 8本はCIDフォントのPDF（うちは字が取れても仮名にならない）、
  1本は古い `.xls`（うちは非対応）。**表の構造も保つ。**
- **うちだけ読めた7本**: すべて anydoc が `NeedsOcr` で降りたもの。
  実際には本文が入っており、うちは読めている。**anydocの判断が早すぎる。**

### いちばん効いた実例

`www.city.○○.lg.jp/.../tesuuryou20250301.pdf`（粗大ごみ処理手数料の表）

    anydoc : 「アイロン台 400 2 / カセットコンロ（卓上用）400 2 …」表のまま読めた
    うち   : 0字

**これは私たちが「その区は手数料を書いていない」と判定してきた項目そのもの。**

## 決定

**作品本体には入れない。開発時の検算にだけ使う。**

理由:

1. **CLAUDE.md の「作品本体は Python 標準ライブラリのみで動く」を変えない。**
   ruff / jscpd と同じ立場に置く。AI読は「誰でも同じ手順で再現できる」ことが
   売りなので、実行に依存を増やさない。
2. **一方通行の乗り換えにならない。** anydoc が降りる7本をうちは読めている。
   置き換えると、いま読めているものを失う。
3. **検算としての価値は実測で確認できた。** 9本の読み落としが1回で出た。
   これは自分の実装だけを見ていては永久に出ない。

## やること

- `analysis/compare_readers.py` を検算道具として置く（`.venv` 経由でのみ動く）
- **anydocだけが読めた添付は、うちのリーダーの宿題として記録する**
  （CIDフォント対応・`.xls` 対応）。直ったら差が消えることで確かめられる
- **anydocの読みを測定結果に使わない。** 判定に混ぜると再現条件が壊れる

## やらないこと

- 置き換え。**うちが読めて anydoc が読めない7本を失う**
- ホスト側OCR（anydoc の `ocr="hosted"`）。ネットに出るうえ有料で、
  「同じ手順で誰でも再現できる」から外れる
