# 測定ハーネスの設計

Status: 設計（未実装）
関連: [`plans/decisions/measure-to-tool.md`](decisions/measure-to-tool.md)、`.github/workflows/check-pages.yml`

## これは何の設計か

AI読は要するに **自治体サイトに対する評価ハーネス（eval harness）** です。
タスク集合（自治体 × 手続き）にモデルを当て、決まった条件で採点し、結果を比較可能な形で残す。
構造は lm-evaluation-harness や SWE-bench の実行系と同じで、違うのは
**タスクが固定データではなく、生きているWebサイト**だという一点です。

その一点が効いて、普通のevalには無い要求が2つ出ます。

- **タスクが勝手に変わる。** 区がページを直せば正解も変わる。だから1回測って終われない。
- **変化の出どころが2つある。** 点が動いたとき、**サイトが変わった**のか**判定器が変わった**のかを
  切り分けられないと、時系列がただのノイズになる。

いま足りていないのは測り方ではなく、**走らせる側**です。

## いまの姿（実測、2026-08-22）

| | |
|---|---|
| 作業単位 | 自治体 × 手続き（以下 **セル**）。いま 23区 × 3手続き = 69セル |
| 実行 | README の7コマンドを**人が順に叩く**。`discover` → `extract` → `failure_distribution` → `apply_evidence_check` → `score` → `report` → `export_web` |
| 取得 | 同一ドメイン 3秒間隔（`crawler/polite_fetch.py:33`）。**並列は0**（`ThreadPool`/`asyncio` の使用箇所なし） |
| キャッシュ | 3,622ファイル / 270MB。**1自治体あたり約 11.7MB**（3手続き分） |
| 判定 | `claude -p` のサブプロセスが**2箇所**（`extractor/fact_extract.py:84`、`scorer/score.py:143`）。timeout 300秒、**リトライなし**、料金の計測なし |
| セルあたりLLM | 4項目 × 1回、リンク追従でもう1回 → **4〜8回** |
| 状態 | ファイル名（`extract_<muni>_<proc>.json`）が暗黙の台帳。**「未測定はどれか」「何で落ちたか」を持つ場所が無い** |
| 定期実行 | `check-pages.yml` が毎日 JST 8:00。**LLMを呼ばない見張り**だけ既にCIで動いている |
| 較正データ | `scorer/golden/tennyu.csv` — **12行・3自治体・1手続きのみ**。児童手当と粗大ごみは**ゼロ** |
| 測定条件 | `measurement.py` が12個の条件をハッシュ化（`measurement_signature`）。**ここは既に良い** |

**良い前例が既にある。** `check-pages.yml` は「安い見張りは毎日CIで回し、
高い測り直しは変化を見つけてから人が判断する」という形になっている。
ハーネスはこれを**高い側にも広げるだけ**で、新しい思想は要りません。

**一番の穴は較正データです。** 較正が転入届の3区にしか無いので、
来月モデルを上げて点が動いたとき、児童手当と粗大ごみでは
「区が直した」と「判定器が変わった」を**区別する手段が原理的にありません**。
`history.py` の `attribution()` が条件不一致のとき区のせいにしないのは正しい実装ですが、
それは「分からない」と言えるだけで、分かるようにはなりません。

## 設計 — 5つの部品

### ① タスク台帳 `harness/cells.jsonl`

いま一番効くのがこれです。1行1セルの追記式。ファイル名を数える運用をやめる。

```jsonl
{"cell":"setagaya/tennyu","muni":"setagaya","proc":"tennyu","state":"scored","sig":"a1b2c3","run_at":"2026-08-15T…","attempt":1}
{"cell":"nakano/sodaigomi","muni":"nakano","proc":"sodaigomi","state":"failed","stage":"extract","error":"claude -p rc=1","attempt":2}
```

状態機械（片方向。戻すときは新しい行を足す）:

```
pending → discovered → extracted → scored → exported
              ↓            ↓          ↓
            failed ←───────┴──────────┘      （stage と error を必ず持つ）
                ↓
              stale        （sig が現行条件と違う ＝ 測り直しが要る）
```

これが1つあるだけで、**再開・部分再実行・進捗表示・「何が測れていないか」の公開**が
全部同じデータから出ます。いまダッシュボードが「測っていない」を灰色で出せているのも
結局この情報なので、台帳を正にして画面がそれを読む向きに直します。

### ② 再開可能なランナー `harness/run.py`

```bash
python3 harness/run.py --proc tennyu                # 未完了のセルだけ進める
python3 harness/run.py --retry-failed               # 落ちたセルだけやり直す
python3 harness/run.py --stale                      # 測定条件が変わったセルだけ
python3 harness/run.py --cell setagaya/tennyu --force
```

- **冪等。** 完了済みセルは触らない。途中で殺しても、次に続きから走る。
- **1セル1トランザクション。** セル単位で成否が決まる。69セル中3つ落ちても66は進む。
- `export_archive.py --retry-failed` で既に同じ考え方を実装済み（50→60→68件を、
  取れた分を失わずに回収した）。**あれをパイプライン全体に広げる**のがこの部品です。

### ③ 判定の口を1つにする `harness/judge.py`

`claude -p` の呼び出しが2箇所に散っていて、どちらもリトライ無し・料金計測無しです。
1つの関数に集約して、そこに以下を置く:

- リトライ（指数バックオフ、上限3回）と、**失敗をセルの `failed` に落とす**
- **モデルの固定と記録。** `--model` を台帳に書き、`measurement_signature` に既に入っている
  `model` / `model_version` と突き合わせる。ここがズレた測定は混ぜない
- 呼び出し回数とトークンの記録（**いま料金が全く見えていない**）
- 呼び口が1つになると、後述の実行場所の切り替えもここ1箇所で済む

### ④ 較正セットを3手続きに広げる

**これをやらないと、以降の時系列に意味が出ません。** やることは2つ。

- `scorer/golden/jidouteate.csv` と `sodaigomi.csv` を作る（各3自治体 × 4項目 = 12行）。
  転入届と同じ密度なら**人手で1手続きあたり半日**の作業量です。
- 測り直しのたびに較正セルを**必ず一緒に走らせる**。較正の点が動いたら、
  その回の測定は**サイトの変化として公開しない**（`recording_status` に理由を残す）。

`scorer/stability.py` が既に「同じ入力をN回採点してぶれを測る」を実装しているので、
較正の実行系そのものは追加で作らなくてよい。**足りないのはデータの方**です。

### ⑤ 実行場所

`claude -p` は Claude Code のログインに依存していて、GitHub Actions にはそのログインがない。
ここが唯一の構造的な壁です。

| 案 | 動くか | 費用 | 問題 |
|---|---|---|---|
| **A** CI + `ANTHROPIC_API_KEY` | ○ 無人で回る | 呼び出し課金（いまサブスク内で0円） | 全国規模だと費用が読めないまま走り出す |
| **B** セルフホストランナー（この Mac） | ○ 認証はいまのまま | **0円** | Macが起きている必要がある。1台のまま |
| **C** 手動のまま | — | 0円 | 測り直しが人の予定に依存する。いまここ |

**推奨は B → 必要になったら A。**
Bなら**今日の認証のまま、追加費用ゼロで、`workflow_dispatch` のボタンから測り直せる**。
「1台のMacに張り付いている」状態は解けませんが、**人が7コマンド叩く状態は解けます**。
Aに行くのは全国規模を本当にやると決めたときで、そのときは③で料金が見えているはずです。

見張り（`check-pages.yml`）は**いまのまま GitHub-hosted でよい**。LLMを呼ばないので壁が無い。

## 速さ — 礼儀を守ったまま速くできる

いまの逐次実行は**礼儀ではなく実装の都合**です。3秒間隔は
**同一ドメインに対する約束**であって、区が違えばドメインも違う。

- 同一ドメイン 3秒は維持。**ドメイン単位のキューを持ち、キューをまたいで並列に回す**
- 並列度は控えめに 4〜8。相手は区役所のサーバーで、こちらの都合で押してよい相手ではない
- `crawler/url_guard.py` の SSRF ガードは既にあるので、並列化で緩めない

|  | いま（逐次） | 並列8 |
|---|---|---|
| 23区 × 3手続き | 数時間 | 1時間未満 |
| 全国 1,741自治体 × 3手続き | **9日以上** | 1日強 |

全国規模のキャッシュは **1,741 × 11.7MB ≒ 20GB**。
リポジトリには入れられない（自治体サイトの著作物でもある）ので、
**キャッシュの追い出し（LRU / 日数）が全国に行く前提条件**になります。
いまは追い出しが無く、`sha1(url)` で上書きされるだけです。

## やらないこと（と理由）

- **ジョブキュー基盤（Celery / Redis / SQS）を入れる。** セルは69個、全国でも5,223個。
  JSONL 1本とファイルロックで足ります。標準ライブラリのみの制約を壊す価値がない。
- **判定を安いモデルに落として速くする。** 判定器を変えると時系列が切れます。
  速さは並列度で取る。モデルを変えるときは `measurement_signature` が変わるので、
  **前後の点数は繋げずに並べる**。
- **測り直しを全自動で毎日回す。** 変化がない日に測り直すのは、費用も相手サーバーへの
  負荷も無駄です。見張り（毎日・無料）が変化を見つけた区だけ測り直す。
- **セル単位のリアルタイム進捗UI。** 台帳を読めば分かるので、必要になったら足す。
