## 1. 処方箋が「一番重い直し方」しか出していない

### 分かったこと

0点だった区は、**どこも「情報が無い」のではなく「AIが着いた場所が違う」**。

| 区 | AIが着いたページ |
|---|---|
| 世田谷 | 「戸籍・住民登録等」の目次ページ |
| 中央 | 案内用ハブ（実体はさらに1階層下） |
| 墨田 | 電子証明書の代理手続き（転入届本体ではない） |
| 荒川 | 外部の対話式ガイドへの誘導ポータル |
| 台東 | **Word文書（.docx）** ← こちらの不備。修正済み・80点 |

答えられなかった40件の内訳は **「記載なし」39件・「曖昧」1件**。
**「PDF内のみ」「電話でのみ確認可」は0件。**「役所に来い」とは言われていない。

到達クリック数と点数の関係も裏づけになっている。

```
1クリックで着いた区  2区 … 平均 0点
2クリックで着いた区 10区 … 平均57点
3クリックで着いた区 11区 … 平均65点
```

**近いほど点が低い。**早く着くのは目次・ポータルで、実体は奥にあるため。

### 何が問題か

いまの `improvements`（`analysis/export_dashboard.py` の `FIX_TEXT`）は
**「本文にこう書き足せ」の1種類しか出していない。** 直し方の中で一番重い。

軽い順に並べるとこうなる。

| 直し方 | 職員の手間 | 根拠 |
|---|---|---|
| 正しく読ませる | **ゼロ** | 台東区はサイトを1文字も直さず 0点→80点 |
| **リンクを1本足す** | 小 | 世田谷は目次から転入届ページへ辿れなかっただけ |
| 本文を書き足す | 大 | 303文字。**いまの処方箋はこれだけ** |
| 機械向けの案内（llms.txt・構造化データ） | 中 | 未着手 |
| 門番を置く | 中（一度きり） | HTMLを直さない |

**23区 × 何十手続き × 更新のたび、を全部職員の手作業に落とすと回らない。**
「AIは穴の場所と型を示すだけ、埋めるのは職員」という設計は正しさと引き換えに
**職員に無限の宿題を出す構造**になっている。

### 決めること

- [ ] **リンク処方箋を作るか。**「このページへのリンクを、この位置に置く」を出せるようにする。
      材料はある: `crawler/discover.py` は候補ページとスコアを持っており、
      `extractor/extract.py:34` の `MAX_LINKS = 40` に入らなかったページが分かる
- [ ] 世田谷でリンク1本を足すと点が変わるかを**実際に測る**（303文字の実験と同じ形で）

## 2. 門番が集める記録の母数が汚染される（重要）

### 分かったこと

`gatekeeper/demand.mjs` の `isAnswered()` にこう書いてある。

> 何を聞かれたか分からないときは、1つでも答えがあれば取れた扱い

実際に動かして確認した結果。

```
質問なし（学習クローラ想定） → answered = true
「手数料は？」と聞いた場合    → answered = false   ← 本当に集めたいのはこちら
```

学習目的のクローラーは `?q=` を付けずページを取りに来るだけなので、
**「何を聞かれたか分からない」に落ちて、ページに答えが1つでもあれば「取れた」に積まれる。**

### なぜ効くのか

Cloudflare の実測（2025年7月・[記事](https://blog.cloudflare.com/crawlers-click-ai-bots-training/)）:

| 目的 | 2024年7月 | 2025年7月 |
|---|---|---|
| 学習 | 72% | **79%** |
| 検索 | 26% | 17% |
| **人の操作を受けて取りに来た** | 2% | **3.2%** |

**署名するクローラーが増えるほど、記録の大半が学習目的になる。**
そして学習クロールは自動的に「取れた」側に積まれるので、
**「取れずに帰った率」が実際より低く見える。**門番が集めたい信号が薄まる。

### 決めること

- [ ] **質問を持たない来訪を「取れた」に混ぜない。** `isAnswered()` の
      「1つでも答えがあれば true」を、`looking_for` が無いときは `null`（判定不能）に倒す
- [ ] 集計を目的別に分ける（Cloudflare の 学習／検索／人の操作 と同じ切り方）
- [ ] `demand.mjs` の metadata に `via` を保存する。いまは `console.log` にしか残らず、
      **どの口（query / nlweb / mcp）から来たかが集計から出せない**

## 3. 「門番」という名前が、設計と逆の印象を与える

実装は **拒否しない**。署名が壊れていても、鍵が見つからなくても素通しする
（`worker.mjs:215-219` で検証全体を try/catch、`worker.mjs:288` で素通し）。

なのに「門番」は**通さない人**の意味。自治体に「門番を置いてください」と言うと、
**トラフィックを止める装置**に聞こえる。置く側が一番恐れることを、名前が煽っている。

### それでも残っている層（ここが堀）

Cloudflare が「取れなかった」と判定する根拠は、確認できた範囲で**3つだけ**。

1. HTTP ステータスコード（4xx / 5xx）
2. robots.txt のディレクティブとパスの文字列照合
3. Accept ヘッダと Content-Type の不一致

**どれも「ページが200を返したのに、答えが載っていない」を捕まえられない。**

そして自治体サイトで一番起きるのはそれ。
**世田谷区の転入届のページは200を返す。**中身も表示される。
それでも4項目は0点だった。Cloudflare のどの製品も、これを異常として検出しない。

Agent Readiness が採点するのは**形式**（robots.txt があるか、Markdown を配れるか）。
**内容は採点しない。**AEO が測るのは「AIが自社を推薦するか」で、
[記事](https://blog.cloudflare.com/aeo/)自身が対象を Claude と GPT の2つと書いている。
住民の問いに答えられたかではない。

> つまり Cloudflare が押さえたのは
> **入口（誰が来たか・入れたか）と出口（サイトを整えろ）。**
> **「エージェントが帰った後、何が欠けていたか」の中間層は空いている。**

### 追記（2026-08-11）— 上の見立ては2日で証明された

**Cloudflare が 8/4〜8/6 の「Agents Week 2026」で、門番の器を丸ごと出した。**

| いつ | 何 |

| 8/4 | **Cloudflare Wallets / cloudflare.pay** — エージェントに ID と決済を持たせる |

**8/6 は LT を話した当日。**

**「サイトの手前に置いて、コードを変えずに AI 向けの口を出す」は、トグルになった。**

### 何が残ったか

| | 状態 |
|---|---|
| サイトの前に口を置く | **消えた。**Cloudflare がトグルで提供 |
| 来訪の可視化 | **ほぼ消えた。**Cloudflare Agents が「何をして、いくらかかったか」を出す |
| **何を探しに来て、取れずに帰ったか** | **残っている。**Cloudflare が見るのは「エージェントが何をしたか」で、「何が取れなかったか」ではない |
| **そのページに何が書いてあるべきかの知識** | **残っている。**4項目の実測データを持っているのは AI読 だけ |

### 役割が違う（2026-08-11 本人の整理）

```
Cloudflare   配管を出す      口 / 観測 / 身元と財布 / ブラウザ
AI読         中身を判定する  この手続きの4項目が、そのページから取れるか
```

**Cloudflare は口を出すが、その口から何を返すかは知らない。**
世田谷区に口を付けても、**ページに手数料が書いてなければ返るものが無い。**

**そして配管が揃うほど、中身の不在は露出する。**
口ができて、エージェントが身元を持って来られるようになるほど、
「聞いても何も返ってこない」が目立つ。
**今週の発表は、AI読 の問題を消すのではなく、見えやすくしている。**

## 10. ここからどう進めるか（2026-08-05 に本人が示した4つ）

**この4つが、以降の判断基準。迷ったらここに戻る。**

### (1) 置かせてもらって「何もわかりませんでした」にしない

**1件目の設置が、一番重い。**そこで何も出なければ2件目は無い。

いまのままだと**その危険が実際にある**（#2 の母数汚染）。
学習目的のクローラーは `?q=` を付けないので「何を聞かれたか分からない」に落ち、

Cloudflare の実測では AI クローラーの **79%が学習目的**（2025年7月）。

→ **置く前に #2 を直す。**これは「あったら良い」ではなく、
**1件目の設置を無駄にしないための必須条件。**

### (2) 運用を回せること

#9 の通り。**いまは本人しか回せない**（採点に `claude -p` ＝ Claude Code のログインが要る）。

## なぜ隠さないか（この作品の作法）

このリポジトリは公開で、**判定基準も、塞いでいない穴も、設計の欠陥も出している。**
理由は本人の言葉で残しておく（2026-08-05）。

> アイデアそのものに価値はほとんどない。簡単に真似できるレベルのアイデアなら、
> すでに誰かが試しているはずだ。本当に価値のあるアイデアは細部まで作り込む必要があり、
> その発想を持った本人でなければ前に進めにくい。
>
> アイデアは1万人が思いついても、実際に行動するのは2〜3人。
> だからこそ、アイデアはどんどんアウトプットし、賛同者や協力者を見つけたほうがはるかに良い。

**実際、隠していないから「置かせてください」と言える。**
穴を先に開示しているから、置く側は判断できる。

**そして真似できないのは、アイデアではなく細部のほう。**
- 採点のぶれ ±15点 → ±2点（二重計上を突き止めて除去）
- 必須要素28スロットの監査と13件の書き直し
- Word文書を診断ページに選んでいたことに**自分で気づいて直した**（2026-08-05）
- 公開画面の「±2点」が構造上ありえないと**検算で見つけて直した**（同日）

**速さだけなら追い抜かれる。自分の数字を疑えるかどうかは、追い抜けない。**

## 11. 外部のオープンデータと突き合わせた（2026-08-05）

**この作品は、外部のオープンデータを1つも使っていなかった。**
オープンデータのハッカソンの作品として、そこは弱い。試しに1つ繋いだ記録。

### 使ったもの

**東京都住民基本台帳人口移動報告（令和7年）第8表 区市町村別各道府県からの転入者数**
- 東京都総務局 ／ **ライセンス CC BY** ／ CSV ／ UTF-8
- `https://www.toukei.metro.tokyo.lg.jp/jidou/2025/ji25qv0800.csv`
- カタログ: `catalog.data.metro.tokyo.lg.jp`（CKAN API が使える）

区名で **23区すべて欠けずに突合できた**。

### 分かったこと（1つだけ）

**区の規模と、AIに読めるかどうかは、まったく関係がない。**

```
転入者数と点数の相関係数  r = -0.00

転入者数が一番多い 世田谷区（57,653人）→   0点
次に多い          大田区（53,204人）→  60点
一番少ない        千代田区（ 6,910人）→  80点
```

→ **「うちは小さい区だから」「予算がないから」という説明が成り立たない。**
4枚目の主張（原因は「AIの限界」ではなく「ページの書き方」）を、外部データで裏づけられる。

### 分かったつもりで、実は何も言っていなかったこと

「手数料が読めない22区に、年間 **692,310人**（97%）が転入している」

**これはほぼ言い換えでしかない。** 22区/23区 = 96% なので、人数で見ても 97%。
**人口で重み付けしても結論が変わらない。**「22区」を「69万人」と言い直しただけ。

唯一の追加情報は、**一番人が来る世田谷区が0点**だったこと（区の数からは出てこない）。

**数字を大きく見せる言い換えを、発見と取り違えない。**

### 決めること

- [ ] 提出でこの突合を使うか。使うなら「規模と無関係」のほうを使う（人数の方は言い換え）
- [ ] 転入者数の定義を確定する（都内間移動を含むか・外国人を含むか で数字が変わる）
- [ ] **他に繋ぐ価値のある外部データがあるか。**
      規模と無関係だと分かった以上、次に見るべきは「なぜ差がつくのか」を説明できる変数
- [ ] 東京都は **CC BY** で出している。**こちらのデータにはライセンスが無い**（#10-(4)）。
      使わせてもらう側が、使わせない形で出しているのは筋が通らない

## 12. 輪が閉じない（2026-08-06 未明・本人の指摘）

### 断絶

```
測る → ダメと分かる → 直し方も出る → でも直すのは職員 → 実害がない → 直さない
```

**「実害がないから直さない」で止まる。**そして止まったことに誰も気づかない。

しかも**この作品の一番大事な原則（AIに書かせない）が、輪を閉じられない理由**になっている。
安全のために、自動で直せなくしてある。

### 輪を閉じる唯一の道は、いまのところ門番

| | 職員から見えるもの | 直す理由 |
|---|---|---|
| **A だけ** | 「あなたの区は0点です」 | **無い。**説教にしかならない |
| **A ＋ B** | 「今月、手数料を聞かれて37回、答えられませんでした」 | **ある。**取り逃しが数になる |

→ **#4 で「A が B の堀」と書いたが、逆も同じくらい効く。B が無いと A は動機を作れない。**
2つで1つ。片方だけでは製品にならない。

### 摩擦を下げる案 — 処方箋を「差分と承認」にする

いまの処方箋は **markdown をコピーさせる**形。職員が空欄を埋めて、CMS に貼る。摩擦が大きい。

**AI に書かせないのではなく、AI に書かせて人が承認する形にできないか。**

```
AI が差分を出す → 職員がレビューする → 承認して反映
```

捏造は防げて（承認するのは人）、摩擦は「コピーして埋めて貼る」よりずっと小さい。
自治体の CMS にその仕組みは無いが、**源内 / A1 の中でならありうる**（#10-(3)）。

### 決めること

- [ ] 処方箋を「コピペ用テキスト」から「差分＋承認」に変えられるか
- [ ] 門番の記録を、職員が見る画面にどう出すか（いまは JSON と標準出力まで・#9）

## 13. 実測値の鮮度 — 古い値を「いまの値」として返してしまう

門番が返すのは **AI読の実測値そのもの**（`nlweb.mjs` の `toResult`。「作らない・盛らない」）。
返す型も3つに分かれていて、**書かれていなければ `failure` を返し、推測で埋めない**。
何を聞かれたか分からないときは `elicitation` で聞き返す（「黙って取れたに倒さない」）。
**設計としては「間違った情報を渡さない」が守られている。**

**ただし `measured_at` は 2026-07-22 のまま。**

```
区がページを直した → 門番は7月22日の値を返す
                   → 「手数料の記載なし」と答える
                   → 実際にはもう書いてある
```

`measured_at` と出典 URL は必ず付くので**嘘ではない**が、
**受け取る側の AI がその日付を見るとは限らない。**

### 決めること

- [ ] 古すぎる実測値は返さない（有効期限を切る）
- [ ] 返すときに「この値は◯日前のものです」と明示する
- [ ] **定期的に測り直す**（有本さんの「定期測定」がここに効く・#6 #9）
