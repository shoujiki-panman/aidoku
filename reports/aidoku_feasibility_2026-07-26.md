# AI読 実地検証レポート（2026-07-26）

## 先に結論

**「処方箋を足すと点が上がる」は、そのままの形では確認できませんでした。**

正確に言うと、こうです。

- AIが自動生成した処方箋を**そのまま貼っても、点は1点も上がりませんでした**（3区とも）
- その処方箋の**空欄を実際の値で埋めてから貼ると、点は大きく上がりました**（3区とも）

つまり動くのは「処方箋を貼る → 点が上がる」ではなく、
**「処方箋が穴の場所を示す → 人が値を埋める → 点が上がる」** の2段階でした。

これは3つの区で別々に、同じ結果が出ています。偶然ではありません。

## 1. 内省ループは実際に動いたか

### 区ごとの数字（すべて実測、同じ採点コードを通しています）

| 区 | 前 | 生成された処方箋を<br>そのまま貼る | 空欄を実際の値で<br>埋めて貼る |
|---|---|---|---|
| 世田谷区 | **0点** | **0点**（変化なし） | **100点** |
| 新宿区 | **0点** | **0点**（変化なし） | **80点** |
| 港区 | 100点（満点・直す所なし） | — | — |
| 港区（人工的に穴を空けた版） | **60点** | **60点**（変化なし） | **100点** |

港区は最初から満点だったので、比較のために期限と手数料をわざとHTMLから消して（100点→60点）、そこで同じ実験をしました。

### 何がわかったか

**良い知らせ：** ページに文章を足すと、AIは本当に読めるようになります。世田谷区は**303文字**足しただけで0点→100点になりました。仕組み自体は本物です。

**もう一つ良い知らせ：** 採点は、見出しがあるだけでは点をあげません。新宿区では手数料だけを空欄のまま残したところ、そこだけ×のまま80点止まりでした。採点は「書いてあるフリ」を見抜いています。これは採点器が信用できるという証拠です。

**悪い知らせ：** 生成された処方箋は、中身が全部「（ここに必要書類を記載）」のような**空欄**でした。

なぜそうなったか。処方箋を作るAIに「事実を勝手に作るな、わからない所は空欄にしろ」と指示してあるからです。世田谷区も新宿区も、入口のページには必要書類も期限も手数料も**一つも書かれていません**。だからAIは埋めるものがなく、全部空欄にしました。

これは**バグではなく、安全側に倒れた正しい動作**です。ここは弱点ではなく「AIが役所の情報を捏造しない」という仕様として説明できます。ただし「ボタン一発で点が上がる」という見せ方は、事実と違うのでできません。

### もう一つ大きな発見（世田谷区）

世田谷区が0点だった理由は「書いていない」からではありませんでした。**4項目すべて、区の別のページにちゃんと書いてありました。**

入口ページから4階層下（ページID 88）にあり、しかも入口ページのリンク一覧が地域名などのナビゲーションで埋まっていて、AIは詳細ページのURLを受け取れませんでした。AI自身も「それらのURLは提供されたリンク一覧には含まれておらず、追跡不可」と記録しています。

つまり問題は「情報がない」ではなく **「情報はあるのに、AIがたどり着けない」**。これは作品のメッセージとして、むしろ強い題材だと思います。

## 4. 正直に、動かなかったところ

- **一番の想定外：** 「処方箋を貼れば点が上がるはず」が3区とも崩れました。上がったのは人が値を埋めた後だけです
- **新宿区では私のミスもありました。** 処方箋を作るときにページの見出し（H1）を入力から落としてしまい、本文から読めたはずの「窓口での届出が必要」まで空欄にしてしまいました。これを直せば自動でも+40点になった可能性がありますが、**試していないので推測です**
- **判定は各1回ずつしか回していません。** 同じ入力で同じ点が出るか（ぶれ幅）は測っていません
- **実際の区のページは1文字も変えていません。** 手元にコピーしたHTMLを書き換えて測っただけです
- 港区で内省ループを見せられたのは、私が人工的に穴を空けた版だけです。本物の欠けたページでの実証は世田谷・新宿の2区に頼っています

## 検証しきれていないこと（辛口）

【なぜ core_claim_verified を false にしたか】
「処方箋を足すと点が上がる」を文字どおりに取ると、3区すべてで否定された。生成された処方箋をそのまま貼った結果は 世田谷 0→0 / 新宿 0→0 / 港(ablated) 60→60。1点も上がっていない。上がったのは人間が空欄に実値を入れた後だけ（0→100 / 0→80 / 60→100）。基盤メカニズム「ページに文章を足すとAIが読めて点が上がる」は確実に真だが、デモで見せる形（URL入れる→処方箋出る→貼る→点が上がる）は現状のコードでは成立しない。ここを true に丸めると、崩れる前提の上にデモを組むことになるので false にした。

【検証しきれていないこと】
1. ぶれ幅ゼロ検証。全判定が1試行ずつ。0点が偶然でないか、100点が再現するかは未測定。LLM判定なので本番デモ前に最低3回は回すべき。実際 failure_reason は before「曖昧」→after「記載なし」と揺れており（スコアには非影響）、理由付けの安定性は無い。
2. 新宿区のH1取りこぼしは私の実装ミス。修正後に+40点になるという話は完全に推測で、一度も実行していない。報告書にも推測と明記した。
3. 「職員が値を埋める」は本物ではない。私が区の別ページをライブ取得してLLMに「このページの記述だけ使え」と縛って埋めた再現。実際の職員は手元の事実を書くので、作業の質も速度も違う。
4. 港区の内省ループは人工的に穴を空けた版でしか示せていない（元が満点＝天井効果）。本物の欠落ページでの実証は世田谷・新宿の2区のみ。
5. 実サイトは一切変更していない。手元HTMLの書き換え実験なので、実際に区がページを直したら本当に点が上がるかは原理的に未検証。
6. 港区の online_clarity「明記」は「窓口へ届出をしてください。」という一文への依存が強い。4回とも明記で安定していたが、その一文が消えた場合は未検証。

【本番との差・APIまわり】
7. APIの判定ロジックは完全なスタブ。URL文字列から決定的にスコアを生成しているだけで、クロールもLLM判定もしていない。実クロール+LLMを繋ぐと1判定あたり30〜60秒（今日claude -pを9回呼んだ実測）かかるので、同期エンドポイントは実用にならない。非同期必須。
8. 本物の源内Webに登録・疎通していない（アクセス手段が無い）。「仕様書のJSON形状に適合」までしか言えない。「源内互換」と書くと嘘になる。
9. 仕様書自体が「2026年03月時点、試行錯誤中、今後大きく変わる可能性」と宣言している。互換性の主張は日付付きでしかできない。
10. 仕様の穴：認証は本文に記述ゼロ（「認証」「APIキー」でgrepして0件）。x-api-keyは非同期のcurl例3箇所からの推定にすぎない。ファイル入力の形は仕様書内で矛盾（content vs contents、構造も別）。明記されたHTTPステータスは202のみで、実装した400/401/404は常識的な補い。タイムアウト・ポーリング間隔・レート制限・リトライは全て規定なし。

【運用上の引き継ぎ事項】
11. 前セッションのテストサーバーがポート8791で起動したまま残っている（PID 89502）。放置すると次回 Address already in use で詰まる。kill 89502 で解消。
12. server.py は --port 引数を持たない（環境変数 AIDOKU_PORT のみ）。--port を渡すと黙殺されて8791で起動するため、起動したつもりで別ポートを叩いて HTTP 000 になる罠がある。私が実際に踏んだ。
13. agent-readiness リポジトリは読み取りのみ。作業前後で git status --porcelain の出力が空であることを確認済み（キャッシュも scratchpad 側に分離）。

【最大のリスク】
今回わかった構造上の問題として、世田谷区の0点の原因は「情報が無い」ではなく「4階層下にあってリンク一覧がナビで埋まりAIが到達できない」だった。つまりAI読が測っているのは「書いてあるか」ではなく「入口から到達できるか」に近い。この定義のまま点数を出すと、実際にはちゃんと情報を整備している自治体を低く採点しかねない。スコアを公表する作品である以上、「どこまで読んだか（単一ページか、リンクを何階層追ったか）」を必ず併記しないと数字が一人歩きする。実際、新宿区は同じページなのに単一ページ判定で0/4、--followありの過去実測で1/4と条件だけで数字が変わっている。
